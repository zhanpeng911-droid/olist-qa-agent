# Agent 评测说明

当前评测分为三层，三者不能混为一个“通过率”。

## 1. 确定性核心评测

运行：`uv run python tests/run_eval.py`

数据源固定为三张分析宽表的截取样本，共 117 项，覆盖：指标和分组动态 SQL 对账、常见问题确定性取数、自然语言意图路由、低评分单变量FDR与95%置信区间标准、共线性处理规则、多变量Logistic、调整后仍显著变量的分布、订单与商品项粒度、通用双变量方法选择、补充验证、线路跨时间验证、无策略输出边界、SQL安全、协议容错、API失败和性能兜底。

这层全通过只说明代码规则可复现，不说明 DeepSeek 在不同表达下稳定。

## 2. DeepSeek 重复稳定性评测

运行：`uv run python tests/run_model_eval.py --repeat 3`

完整数据库验收运行：`uv run python tests/run_model_eval.py --source mysql --repeat 3`

43 个问题覆盖单指标、复合指标、分组、排名、口语改写、统计方法、三个受控目标的关联因素分析、目标变量边界、补充验证、分析粒度边界和多步骤问数。程序同时报告总体指标与调用大模型的子集指标，并把逐次轨迹保存到 `artifacts/evaluations/`。

每题完成后都会立即更新报告；模型输出非法工具参数时，该题记为失败并继续执行，控制台会直接显示失败原因。因此 FAIL 是稳定性证据，不能为了得到100%而删除，但单题失败不应造成整批测试崩溃。

建议先用 `--case-ids M-01,M-21,M-31,M-34 --repeat 1` 做代表性检查，再运行完整重复评测。模型结果应按类别查看失败案例，不能只看总体百分比。

## 3. 完整 MySQL 业务数据库页面验收

按照 `tests/manual_acceptance_questions.md` 依次测试指标查询、双变量统计、三目标关联因素分析、补充验证和安全边界。演示样本只验证功能路径，业务数值和性能必须在完整数据库模式中验收。

## 4. 关键故障回归题

`分析低评分率与路线是否有显著相关`

- 必须识别为 `statistical`，不得进入普通 ReAct 问数；
- 线路是高基数分类变量，低评分是二分类变量，方法固定为 Pearson 卡方独立性检验并报告 Cramér's V；
- 数据库端只返回 `route × is_low_score` 聚合计数，应用端过滤小样本线路后检验，不把全量明细传给大模型；
- 返回 p 值、效应量、样本量、稀疏列联表条件和“相关不等于因果”的边界。

`深度验证是否延迟、延迟程度、总履约时长、地区、跨州及高风险线路与低评分的关系`

- 必须识别为 `deep_validation`，不得退回普通线路卡方检验；
- 必须覆盖用户点名的全部变量；
- 核心因素使用多变量Logistic调整并报告OR/95%CI/校正后p值；
- 高风险线路必须从较早时期数据中产生，并用较晚20%的订单验证关联方向；
- 深度结果不自动生成治理动作。
