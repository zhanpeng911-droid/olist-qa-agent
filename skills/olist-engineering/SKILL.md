# Olist 数据工程

## 目标与权限

接收已校验的九表批次，模型规划并生成 Staging / Mart SQL。程序提供确定性CSV解析和安全Raw增量合并；不是由模型逐行猜测和修复原始业务值。只支持已登记的Olist九表合约，不声称能自动理解任意行业数据。

1. inspect_batch：检查九表逻辑行数、冲突/无效记录、源日期范围、merge_mode 和 snapshot_at。源文件没有更新时间/删除事件，不能推断不存在的删除或新旧关系。append_only 不覆盖旧键；upsert 必须具有可信、带时区且晚于水位的提取时间。
2. inspect_schema：查看已发布业务表及其粒度。先说明构建计划；有必要的业务定义缺失则 ask_user，不能自行补造。
3. prepare_workspace：调用工具自主建立/连接隔离数据库，复制正式Raw并合并本批数据。只生成候选Raw，不发布。工具返回候选库名、合并计数和Raw质量门。正式库保持可用。Raw解析/合并由可信代码完成，LLM不可DROP/改写Raw。
4. reference_sql(table)：按需读取现有建模SQL作为参考，不是自动执行器；该工具返回SQL字符串。必须在 execute_sql 中提交实际 SQL 才会执行。可以依据任务改写表达式/索引/聚合，但必须保持报表兼容字段与业务口径。每条SQL独立提交，也可一次提交最多八条以顺序执行；失败停止本次列表，读取错误后重建对应候选表。
5. 建四张Staging：stg_geolocation_zip按邮编一行、stg_order_payments按订单汇总支付并选主要方式、stg_order_reviews每订单选择最新回答时间的评价并定义低评分<=3、stg_order_items_summary按订单聚合商品/卖家/品类。先聚合后连接，不因一对多复制订单。
6. 建三张Mart：mart_order_delivery订单一行、mart_order_seller_delivery订单—卖家一行、mart_order_item_business订单—商品项一行。字段与参考定义保持兼容，包括订单/卖家/商品项金额、评分来源、时间有效性、最终日历日延迟、邮编地理、品类与支付信息。所有原订单必须保全。未知评分/延迟保持NULL或有效性标记，不伪造为0。
7. validate_candidate：运行固定36项校验，包含Raw关系、建模粒度、订单保全、来源标记、评分/延迟口径、原始/聚合/明细金额对账。FAIL阻止发布；WARNING保留缺失数量并解释。检查失败时 inspect_schema / run_query 排查并修正生成SQL，最多连续修复三次。只通过校验不能证明任意新增字段业务正确，须在回答指出重要改写及其验证。
8. 质量门通过后停止在“待确认发布”，下一轮直接总结批次范围、合并计数、生成SQL和校验结果，不为已经通过的固定检查再执行重复对账或反复读取schema。WARNING应据实际校验摘要解释；新增字段确有单独验证需求时应在validate_candidate之前完成。没有可由模型调用的publish工具；用户确认后后台复核正式库版本与质量门，再原子切换，并保留旧版本。基础库在任务中变化时必须重新构建，不覆盖他人更新。

每轮最多8次工具调用，每个execute_sql最多8条语句，按依赖顺序批量提交；全任务最多24轮/80次工具调用/350,000累计token。已执行SQL的重复回执和已使用参考会在后续模型上下文中压缩，但实际SQL与完整执行历史保留在本地审计。不能以提高预算、绕过权限或删除校验来宣称工程完成。

## 工具与资料边界

只能读取注册skill、四份建模参考SQL、当前批次校验摘要及白名单表结构。不读取.env、密码、任意本地文件，不运行shell。所有SQL写入仅发生在本任务候选库的四张Staging和三张Mart。无DROP DATABASE、GRANT、用户管理、DELETE或正式库任意DML。技能说明约束执行思路；AST检查、数据库只读事务/候选库约束和固定质量门才是执行权限边界。
