## 2. 你需要重点审核的地方（数据分析侧）

### 2.1 口径定义（最重要）→ `semantics/metrics_dict.yaml`
- 核对：`is_low_score`(≤3)、`is_strict_negative_score`(≤2)、`late_rate`、`on_time_rate`、`avg_late_days` 等指标表达式是否符合你心中的口径
- 核对：`min_group_sample=100`、`multi_seller_rule`（卖家/线路默认 `is_multi_seller_order=0` 去重）、`text_boundary`（无评价正文不臆测）
- ⚠️ **真库字段名需与此字典一致**（`is_late_delivery` / `late_days` / `is_low_score` 等），有出入在此对齐

### 2.2 统计方法 → `agent_core/statistics.py`
- 核对：单变量检验方法选择（2×2 卡方/Fisher、R×C 卡方+Cramér's V、趋势 Cochran-Armitage、MWU+效应量、Spearman）
- 核对：Logistic 是否用 HC3 稳健 SE、公式里的变量选择是否合理（`4.5` 的模型约束）
- 核对：证据分级规则（强/中/待验证）是否与你预期一致

### 2.3 归因逻辑 → `agent_core/attribution.py`
- 核对：优先级综合分 = 超额低评分 × (Lift-1) 的合理性；P0/P1/P2 分位数划分
- 核对：route 动态阈值 `max(15, 卖家样本×2%)` 是否合适（高基数维度）
- 核对：候选维度清单是否覆盖你关心的因素

### 2.4 建议规则 → `config/recommendation_rules.yml`
- 核对：6 条规则的责任方/动作/监控指标/验证方式是否符合业务现实
- 扩充：真库验证后，按真实业务补充更多规则（卖家、线路、品类等）

### 2.5 样例数据合理性 → `scripts/generate_sample_data.py`
- 核对：注入的"延迟→低评分率单调上升"模式是否真实反映 Olist 业务（样例用于演示，真库才是准的）

## 5. 协同开发约定

1. **提交前必过测试**：`uv run pytest tests/`（44）+ `uv run python tests/run_eval.py`（26）
2. **改口径必更字典**：任何指标/维度口径改动，必须同步 `semantics/metrics_dict.yaml`
3. **改代码必记台账**：每次变更追加到 `tests/TEST_LOG.md`（含修复的问题、测试结果）
4. **`.env` 绝不提交**（已 .gitignore）：含 DeepSeek key 与数据库密码，各自本地维护
5. **分支建议**：`main` 保持稳定可跑；新功能开分支，合并前过测试
6. **字段名标准**：以《低评分归因与改善建议Agent搭建思路》命名（`is_late_delivery` 等）为准，改动需双方确认
