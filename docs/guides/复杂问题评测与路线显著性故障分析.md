# 复杂问题评测与“线路—低评分”故障分析

## 1. 原问题为什么会挂起或没有答案

问题：`分析低评分率与路线是否有显著相关`

原程序只把“归因、为什么、原因、改善建议”等识别为复杂分析；这句话虽然含“显著相关”，却会因“低评分率”被当成普通问数。随后产生一条故障链：

1. 普通 ReAct 工具只会分组取数，没有显著性检验工具，大模型只能反复尝试查询；2. 全量库线路较多，若反复读取、排序或把大量分组结果回传模型，执行时间和上下文都会放大；3. DeepSeek 客户端原先没有明确超时，网络或模型等待时页面看起来像“挂掉”；4. 模型偶尔返回 Markdown 代码围栏包裹的 JSON，原解析器只接受纯 JSON；5. 达到最大步骤后程序返回空字符串，界面最终只显示“未得到答案”。截取 CSV 数据量更小，只减少了查询时间，并没有补上统计方法，因此仍可能没有答案。

## 2. 正确的分析路径

这不是简单的数值比较，而是“高基数分类变量 × 二分类结果”的独立性检验：

- 因素：线路（如 `SP→RJ`），名义分类变量；
- 结果：是否低评分，二分类变量；
- 主方法：Pearson 卡方独立性检验；
- 效应量：Cramér's V；
- 不应使用：Pearson 或 Spearman 相关系数，因为线路没有连续数值或自然顺序；
- 稀疏处理：先过滤样本量过小的线路，再检查期望频数条件；条件不满足时不下“显著/不显著”的强结论。

现在的执行顺序为：

```text
自然语言问题
  → statistical 意图
  → 识别因素、结果变量及变量类型
  → 固定选择统计方法
  → MySQL 只聚合 route × is_low_score 的计数
  → Python 过滤小组并完成卡方与 Cramér's V
  → 返回方法理由、p值、效应量、样本量、假设条件和业务边界
```

全量数据库不再把订单明细交给模型。即使有约 10 万订单，应用收到的也只是每条线路两行计数，计算规模取决于线路数而不是订单数。

## 3. 本次可靠性改造

1. 新增统计问题专用路由，覆盖显著、相关、关联、检验、差异、p 值、置信区间等表达；2. 按变量类型固定选择 Pearson 卡方/Fisher、Cochran–Armitage 趋势检验、Mann–Whitney U、Spearman 或 Kruskal–Wallis；3. DeepSeek 默认 45 秒超时、最多一次重试；4. ReAct 解析兼容纯 JSON、代码围栏 JSON 和前后带少量说明的 JSON；5. 空答案、步数耗尽和 API 异常均返回可理解的非空错误，不再直接崩溃；6. 人工模拟 CSV 和生成脚本已删除，统一使用 `data/sample/` 中三张真实 Mart 截取 CSV 做本地回归。

## 4. 新评测体系为什么更可信

### 确定性核心评测

`tests/eval_questions.yml` 共 84 项，使用项目截取 CSV，动态检查工具结果与 SQL 重算是否一致，并覆盖意图、归因、统计方法、商品项粒度与显著性、模型降级、显著特征总结、深度验证候选、策略证据门槛、安全和异常兜底。

这层全通过只表示代码逻辑可复现，不能证明大模型稳定。

### 真实模型重复评测

`tests/model_eval_questions.yml` 共 30 个自然语言问题。运行：

```powershell
.\.venv\Scripts\python.exe tests\run_model_eval.py --repeat 3
```

程序分别报告：

- 意图准确率：问题有没有进入正确处理路径；
- 完成率：是否产生非空结果；
- 正确工具路径率：表、指标和维度是否选对；
- 重复一致率：同一问题多次运行的工具路径是否一致；
- P50/P95 延迟：不仅看平均速度，也观察慢请求尾部。

因此不能再用一次运行的“100%”直接宣称模型稳定。若某类问题失败，应按问题类别和执行轨迹定位，而不是只看总体分数。

## 5. 全量 MySQL 复测方式

电脑重启后，页面中的会话密码会丢失。重新启动 Agent，在左侧选择“真实 MySQL”，输入 Workbench 使用的密码并测试连接，然后再次提问原问题。预期结果应直接出现统计分析卡片，不调用 DeepSeek，也不会等待模型规划。

复测时重点核对：执行时间、有效样本量、纳入/排除线路数、期望频数条件、p 值和 Cramér's V。即使 p 值显著，也只能说线路和低评分存在观察性关联；治理优先级还要同时考虑效应量、低评分规模和可干预性。
