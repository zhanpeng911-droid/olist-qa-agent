# 数据工程 Agent：任务验收与复测指南

## 判断标准

验收的问题不是“页面能否打开”，而是：**九表能否正确接入；补充时间段后，三层数据和报表是否完整更新；重叠输入和错误输入是否会破坏已发布数据。**

本指南仅验收固定工程流程下的CSV接入、增量合并、SQL建模、质量检查和经营报表，不调用DeepSeek。当前另有LLM自主工程和动态取数，其真实模型调用、澄清和语义正确性须另外验证，见 [MU测试指南](MU测试指南.md)。旧归因Agent的M测试不适用于本版。

| 场景 | 输入／操作 | 通过标准 |
|---|---|---|
| 首次建库 | 原始数据按订单购买时间拆出 2018 年前批次 | 45,430 笔订单；九张 Raw、四张 Staging、三张 Mart 构建完成；36 项质量检查无 FAIL |
| 补充新时间段 | 通过上传接口提交 2018 年及以后九个文件 | 订单扩展至 99,441 笔；历史订单保留；三张 Mart 和报表同步更新 |
| 重复／重叠导入 | 再提交原始全量快照 | 九表新增和更新为 0；行数、金额不变；规则未变时为“未变化”，不新增版本／备份 |
| 更新保护 | 默认追加提交变更商品；再提供更晚源快照 | 默认拒绝覆盖；显式新快照更新成功；旧／同时间快照拒绝 |
| 状态与完整性 | 状态回退；新增已送达但无商品项订单 | 均拒绝发布，已发布数据不变 |
| 备份管理 | 预览、错误确认目标 | 当前上一版受保护；不一致确认不得删除；U 在专属测试备份中验证精确清理 |
| 源数据对账 | 比较原文件、快照和 Raw | 九表逻辑记录数一致；源文件 SHA-256 一致；复杂评价文本完整保留 |
| 字段／取值错误 | 错误列名、评分 6 分 | 校验失败；不允许执行发布；已发布数据不变 |
| 引用错误 | 支付记录引用不存在的订单 | 源格式可以通过，但三层质量门必须拒绝发布；已发布版本不变 |
| 版本恢复 | 尝试恢复非当前版本，再依次恢复当前版本 | 非当前版本被拒绝；有效恢复后行数、金额和版本标记一致 |
| A／B 报表 | 读取默认周期、州筛选及增长页 | 指标与已送达口径一致；州、品类、卖家全部贡献金额对账；无 2018-09 虚假零值尾部 |
| Mart 导出 | 下载三张 Mart CSV | 可按标准 CSV 完整解析；字段数一致；逻辑记录数等于对应表行数 |
| 正式库保护 | 测试前后只读对账 | 正式库 16 张业务表行数以及订单 Mart 商品金额、运费不变 |

时间分批使用订单购买时间，商品项、支付和评价随 order_id 分批。无可靠时间字段的维度表在两个批次中提供完整快照。不能把客户、商品或地理表机械地按订单年份裁切。

## 自动复测

启动 MySQL80 后，在 PowerShell 中运行：

```powershell
cd "C:\ShouldStudySoStudy\internship\DataAnalysisAgent\olist_qa_agent\v2"
.venv\Scripts\python.exe -m pip install pytest httpx

# 解析、指标、HTTP 状态保护及 MySQL 合并规则回归
$env:OLIST_TEST_MYSQL='1'
.venv\Scripts\python.exe -m pytest -q -p no:cacheprovider --basetemp artifacts/test_tmp

# 实际 HTTP 接口全流程验收：目录接入、上传、校验、发布、导出和恢复
.venv\Scripts\python.exe scripts\run_task_acceptance.py
```

全流程验收使用原始九张 CSV，不替换为模拟业务样本。错误场景由原始字段结构构造最小错误批次。脚本创建 `olist_accept_<随机标识>` 隔离数据库，并启动一个独立的本机测试服务；不会修改 `.env`，也不会发布到其中配置的正式库。无需关闭当前页面，但不要同时在正式页面执行数据构建。

U 与 M 请按上述顺序串行运行。发布、恢复和备份清理共用 MySQL 全局互斥锁；同时运行时，某个测试可能被正常的并发保护拒绝，这不等于数据逻辑失败。等待其他任务结束后再跑完整测试，不应关掉互斥检查来追求测试通过。

脚本逐阶段输出进度，结束时必须同时看到 `TASK_ACCEPTANCE=PASS` 和报告路径。只有进程退出码为 0、JSON 顶层 `status` 为 `PASS` 且每项场景通过，才算完成验收。若输出 FAIL，应按 JSON 中的错误和同目录 `service.log` 排查，不能将已通过的部分场景当作整体通过。

结果保存在：

```text
artifacts/engineering/task_acceptance_<随机标识>/
  acceptance.json       每项场景、计数、质量告警与测试结论
  service.log           独立服务日志
  before_2018/          真实历史批次
  2018_and_after/       真实新增时间段
  batches/              上传快照、批次状态和规范化记录
```

独立测试服务结束后自动停止。验收库、失败候选库、备份库和测试文件保留供复核，没有自动清理策略；多次全量验收会占用磁盘空间。`artifacts/test_tmp` 仅用于 pytest 临时文件，测试会清理其中内容，不应存放业务数据。

`scripts/verify_incremental.py` 仍保留，直接验证构建函数；日常任务验收优先使用 `run_task_acceptance.py`，因为它还覆盖网页依赖的 HTTP 接口与后台任务状态流转。

## 手工检查页面

自动验收覆盖数据流程及接口，不能代替所有浏览器操作与视觉检查。打开当前页面后可补做：

1. 数据工程页：查看九表文件要求、批次阶段、合并计数、质量检查和错误明细；源校验通过仅表示可执行，只有“已发布”才表示三层数据已更新。
2. A 页：默认 2017-01 至 2018-08，应显示已送达订单 96,211 笔、客户 93,104 名、商品金额 R$13,181,027.13、商品客单价约 R$137.00；切换 SP 后指标应改变。
3. B 页：对照 2017／2018 年 1–8 月，商品金额增幅约 141.13%，订单增幅约 139.94%；州筛选与 A 页一致，恢复默认后恢复全平台指标。
4. 查看图表是否正确显示，尾部不应因生成一个无业务数据的月份而骤降；下载按钮应得到可解析的 CSV。

首次导入、错误批次和回滚的手工尝试应在独立库完成，不要为练习而恢复正式库。正式库未发布全量时，上述全量数字不一定适用。成功轮询或页内刷新应清除旧连接错误；任务失败原因则仍应保留。切换到快照更新模式应出现源快照时间字段；备份管理先预览，确认删除后无法恢复。

## 如何解释验收结果

源文件的行数指 CSV **逻辑记录数**，不是按换行统计的物理行数。Staging 是去重或订单聚合，不能要求它与 Raw 行数相同。

质量检查中的 WARNING 表示已识别且保留的源数据异常，如缺少支付、时间顺序异常或缺少地理信息；不等同于导入失败。FAIL 则必须阻止发布。三层对账的全部订单金额也不等于报表“已送达、指定月份”金额，比较时必须统一口径。

通过这些场景说明当前九表合约下的任务已得到验证，不代表任意数据规模、字段变更、并发外部写入或机器断电都已覆盖。快照时间必须可信，CSV 没有删除事件；评价和地理位置没有稳定事件键，无法辨别完全相同的新事件与历史快照。接入前仍需核对上游业务键、更新语义和维度完整性。新版 M 指完整任务验收，不是旧 M 模型调用测试。
